# Generated base schemas: both kinds of list

Generated from the core model [base/model/lote_model.json](../model/lote_model.json), which describes what clause 6.3.0 allows for **both** kinds of list. **Do not edit these files**: change the model or the generators, then regenerate.

Here, explicit and implicit scheme information are rules: Table 1 is `R-Table1` and the placement of the list information is `R-SchemeInfoPlacement` (`ListAndSchemeInformation`, or the five list elements directly in the list, never both). ## Profiles (Annexes D–I)

The profiles are generated into [explicit/generated/profiles/](../../explicit/generated/profiles/): every annex requires a scheme explicit list (D.1–I.1), so each profile builds on the explicit track. Per annex: a JSON profile (`lote_profile_<X>_<name>.json`: `allOf` the explicit track's `../base/lote_core.schema.json` plus the annex's constraints) and a Schematron file (`lote_profile_<X>_<name>.sch`) used with the explicit track's `base/lote_core.xsd` and `base/lote_core.sch`. Generated by [gen_profiles_from_model.py](../../src/lote_schema_generator/gen_profiles_from_model.py) from the overlays in [explicit/model/profiles/](../../explicit/model/profiles/).

Every rule carries an id and the citation of the annex sentence it enforces, so a failure can be traced to the text:

- **Rule ids:** `<annex>-<component>-<required|prohibited|fixed|values>` for structural rules (e.g. `D-LoTEType-fixed`), the constraint key for invariants (e.g. `D-te-tel`). The ids are the overlay elements' `id`s and are unique per annex (the build checks).
- **Schematron:** `<sch:assert id="D-te-tel">` (the pattern is `p-D-te-tel`); the message is `[id] rule. Table row (p. N, line L): "quote"`.
- **JSON:** each rule is its own `allOf` entry with `$anchor` and `title` set to the id and a `description` with the rule and citation. Rules JSON Schema cannot express are listed in `x-rules-layer` (id, rule, `check`, row, citation) and in `$comment`.

[tools/lote_validate.py](../../../schema_validator/src/lote_schema_validator/validate.py) validates a list with these files and prints each failure with its rule id, location and citation.

They replace the hand-coded data of the earlier `gen_profiles.py` (which still writes `core/profiles/`). Differences from those: the F and G rules-layer lists now state what F.3 and G.3 actually require (certificates that distinguish access / registration certificates, not certificates that certify the TEName), and XML profiles exist at all.

## Model validator limitations

- **There is no signature validator.** [tools/lote_validate.py](../../../schema_validator/src/lote_schema_validator/validate.py) does not check whether a signature is valid: not the envelope (the compact JWS around a JSON list, `ds:Signature` in or around an XML list), not the JAdES / XAdES header, not the signing certificate and not the cryptographic signature. The model records what such a validator would check: the `Signature` component (`"validation": "not-schema-based"`), and the constraints `R-Signed` (6.8.0: the list shall be signed, AdES baseline B) and `R-SignerMatchesOperator` (6.8.0: the certificate's C and O match the scheme territory and operator name). Today the validator checks only where a signature may or must sit: no `Signature` component in a JSON list (6.8.0), `ds:Signature` optional in XML, required in an Annex H list in XML (H.4).

## Regenerate and test

```bash
cd schema_generator                             # with the package installed: pip install -e ".[dev]"
lote-schemas build                              # the whole chain: schemas and profiles (see pipeline.py)
pytest                                          # core and profiles in JSON and XML, the tracks, the checker, the build
lote-schemas check explicit/generated/base/lote_{core,tie,sie}.xsd --scheme explicit
lote-schemas check implicit/generated/lote_{core,tie,sie}.xsd --scheme implicit
```

## XML binding notes

- **Element order:** the text decides what a list contains; the order of XML elements follows the Forge XSD (model/README.md, Conventions). All structures have Forge's order; `OtherLoTEPointer` deviates from the text's listing on purpose (`ServiceDigitalIdentities` before `LoTELocation`).
- **Extensions:** the extension elements (`tie:OtherAssociatedBodies` with its `tie:AssociatedBody` items, `sie:ServiceUniqueIdentifier`) are in their extension namespaces; the members of an associated body are core components, so they are in the core namespace. Extension content inside `Extension` is validated (`processContents="lax"`), because the core imports both extension schemas.
- **Plain text:** XSD regular expressions have no look-ahead, so U+FEFF is excluded everywhere in multilingual strings, not only at the start (Annex B.2 3). Slightly stricter than the text.
- **Imports:** the core imports `xml.xsd` and the XML-signature schema from w3.org, so compiling it needs network access the first time.
