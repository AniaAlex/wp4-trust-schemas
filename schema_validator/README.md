# schema_validator

Validates lists of trusted entities (ETSI TS 119 602 V1.1.1, LoTE), in XML or JSON, against the schemas generated by [../schema_generator](../schema_generator/), and reports every failure with the sentence of the spec it breaks: rule id, location in the list, clause or annex row, page, line and quote.

## Install and use

```bash
pip install -e ".[dev]"

lote-validate list.json --profile D       # explicit track + Annex D (PID providers)
lote-validate list.xml --explicit         # explicit track (Table 1, explicit column)
lote-validate list.json --implicit        # implicit track (Table 1, implicit column)
lote-validate list.json                   # track inferred from the content
lote-validate list.xml --profile H --json # machine-readable: {"track", "track_reason", "profile", "findings"}
```

```python
from lote_schema_validator import validate

report = validate("list.json", profile="D")
report.valid, report.track, report.track_reason
for f in report.findings:
    print(f.layer, f.rule, f.location, f.message, f.source)   # source: ref, page, line, quote
```

Exit code of `lote-validate`: `0` valid, `1` failures, `2` usage error.

## Example finding

```
[profile-D] D-te-tel
  at   /lote:ListOfTrustedEntities/lote:TrustedEntitiesList/lote:TrustedEntity[1]/lote:TrustedEntityInformation/lote:TEAddress
  why  The electronic address contains a contact phone number (tel: URI).
  spec Table D.2 TE address, p. 48, line 2931: "contact email and contact phone number"
```

## Layers

| Layer | XML | JSON |
|---|---|---|
| Track structure | `schemas/<track>/generated/lote_core.xsd` | `schemas/<track>/generated/lote_core.schema.json` |
| Track rules | `schemas/<track>/generated/lote_core.sch` | (in the JSON Schema) |
| Profile | `schemas/explicit/generated/profiles/*.sch` | `schemas/explicit/generated/profiles/*.json` |
| Rules JSON Schema cannot express | (in the Schematron) | the profile's `x-rules-layer` checks, e.g. the 6-month `NextUpdate` rule |

## Schemas

[src/lote_schema_validator/schemas/](src/lote_schema_validator/schemas/) is package data: a copy of the generator's output (both tracks with their model snapshots and schemas, the D–I profiles, and the model files the citations come from). It is written by `lote-schemas publish` in the generator project; do not edit it. Set `LOTE_SCHEMAS_DIR` to validate against another copy.

## Tests

```bash
pytest
```

[tests/data/](tests/data/) holds sample lists (valid D and H lists, explicit and implicit lists, and lists that break 6.8.0, H.4 and Table 1), written from the generator's test builders. `test_published_schemas_are_current` compares the package data with the generator's output when the generator project sits next to this one.

## Limitations

- **There is no signature validator.** Whether a signature is valid (the envelope, the JAdES / XAdES header, the signing certificate, the cryptographic signature) is not checked. The schemas check only where a signature may or must sit: no `Signature` component in a JSON list (6.8.0), `ds:Signature` optional in XML, required in an Annex H list in XML (H.4).
- **Network on first XML run:** the XSD imports `xml.xsd` and the W3C XML-DSig schema from w3.org.
- Rules-layer requirements no program can check (listed in each profile) are not checked.
