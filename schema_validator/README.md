# schema_validator

Validates lists of trusted entities (ETSI TS 119 602 V1.1.1, LoTE), in XML or JSON, against the schemas generated by [../schema_generator](../schema_generator/), and reports every failure with the sentence of the spec it breaks: rule id, location in the list, clause or annex row, page, line and quote.

## Install and use

```bash
pip install -e ".[dev]"

lote-validate list.json                   # explicit track + the annex the list's LoTEType names (D-I), if any
lote-validate list.json --profile D       # explicit track + Annex D (PID providers), whatever the list declares
lote-validate list.xml --no-profile       # explicit track only (Table 1, explicit column)
lote-validate list.xml --profile H --json # machine-readable: {"track", "profile", "profile_reason", "declared_profile",
                                          #                   "warnings", "findings", ...}
```

```python
from lote_schema_validator import validate

report = validate("list.json")                  # profile=None: from the LoTEType; "D": Annex D; False: none
report.valid, report.track, report.profile, report.profile_reason, report.warnings
for f in report.findings:
    print(f.layer, f.rule, f.location, f.message, f.source)   # source: ref, page, line, quote
```

Exit code of `lote-validate`: `0` valid, `1` failures, `2` usage error.

**Which profile is applied.** Each annex fixes the list's `LoTEType` (Tables D.1–I.1, e.g. `http://uri.etsi.org/19602/LoTEType/EUPIDProvidersList` for D). Without `--profile`, `lote-validate` applies the annex whose `LoTEType` the list declares, and says so in the first line of the report (`profile D (from its LoTEType …)`); a list whose `LoTEType` names no annex, or that has none, is checked against the explicit track only. `--no-profile` forces the track only. When `--profile` names another annex than the list declares, the profile is still applied, and the report starts with a warning:

```
list.json: explicit track (...), profile E (--profile E) - 7 failure(s)
WARNING: The list declares LoTEType http://uri.etsi.org/19602/LoTEType/EUPIDProvidersList (Annex D) but was checked against profile E. Did you mean --profile D?
```

Every list is validated as a **scheme explicit** list: WP4 lists are explicit, and the implicit track is frozen and not published ([project_decisions_vs_etsi.md](../docs/project_decisions_vs_etsi.md) #3, #4). A list without the scheme information fails with the Table 1 rules (`EXP-SchemeName-required`, …); it is never accepted as an implicit list.

## Example finding

```
ERROR: [profile-D] D-te-tel
  at   /lote:ListOfTrustedEntities/lote:TrustedEntitiesList/lote:TrustedEntity[1]/lote:TrustedEntityInformation/lote:TEAddress
  why  The electronic address contains a contact phone number (tel: URI).
  spec Table D.2 TE address, p. 48, line 2931: "contact email and contact phone number"
```

## Rule ids

Every finding has a rule id from the model, and its citation is looked up by that id. Nothing is matched by element name alone.

| Finding from | Rule id | Example |
|---|---|---|
| Profile (Annexes D–I) | the overlay element's id | `D-LoTEType-fixed`, `D-Signature-json-prohibited` |
| Core rule | the model constraint's key, or the Schematron pattern | `R-StatusWithHistory`, `ElectronicAddressContent` |
| Track rule (Table 1, 6.3.0) | the `scheme` id of the component in the track's model | `EXP-SchemeName-required`, `EXP-NextUpdate-prohibited`, `IMP-SchemeName-prohibited` |
| XSD or JSON Schema error | the model place of the error's location, plus what is wrong | `PostalAddress-Country-required`, `TEAddress-ElectronicAddress-not-allowed`, `ServiceInformation-ServiceName-value`, `LoTE-Id-not-allowed`, `LoTE-root` |

For XSD and JSON Schema errors, the error's location in the list (the element path or the JSON path) is followed through the track's model, one step at a time, to the structure or component it is in. Helper elements inside a value (`Name`, `URI`, `dateTime`) belong to their component, so an empty `URI` in an electronic address is `SchemeOperatorAddress-ElectronicAddress-value` and cites clause 6.3.5.2. A forbidden component (`max: 0` in the track model) is found in the structure where the error occurs, so `NextUpdate` directly in an explicit list cites 6.3.0, while a `NextUpdate` inside a `PostalAddress` is `PostalAddress-NextUpdate-not-allowed`.

## A wrong root element

XSD validation starts at the root, and the profile Schematron rules name their elements from the root, so a list whose root element is wrong would otherwise get no further checks. When the root is not `lote:ListOfTrustedEntities` but its children are LoTE components in the LoTE namespace, `lote-validate` reports `LoTE-root` and then checks the rest of the list as if the root were right. Only the root's name is changed, in memory: the file is not modified and nothing is written. Locations in the report are those of the file (`/TrustedEntitiesList/lote:ListAndSchemeInformation/...`), the report says that the root was corrected, and `--json` has `"root_corrected": true`. The list still fails (exit code `1`). A root around content that is not a LoTE is reported as `LoTE-root` only.

## Layers

| Layer | XML | JSON |
|---|---|---|
| Track structure | `schemas/<track>/lote_core.xsd` | `schemas/<track>/lote_core.schema.json` |
| Track rules | `schemas/<track>/lote_core.sch` | (in the JSON Schema) |
| Profile | `schemas/explicit/profiles/*.sch` | `schemas/explicit/profiles/*.json` |
| Rules JSON Schema cannot express | (in the Schematron) | the profile's `x-rules-layer` checks, e.g. the 6-month `NextUpdate` rule |

## Schemas

[src/lote_schema_validator/schemas/](src/lote_schema_validator/schemas/) is package data: a copy of the generator's output. It is the generator's `explicit/` directory, in the same layout, without its documentation:

```
schemas/
  explicit/
    generated/base/      the explicit track's schemas (JSON Schema, XSD, Schematron)
    generated/profiles/  the Annex D–I profile schemas
    model/               the files the citations come from (never used to decide validity):
                         lote_model_explicit.json and profiles/ (the Annex D–I overlays)
```

The track's documentation (structure, terminology, known gaps) is in the generator: [../schema_generator/explicit/](../schema_generator/explicit/).

It is written by `lote-schemas publish` in the generator project; do not edit it. Set `LOTE_SCHEMAS_DIR` to validate against another copy.

## Limitations

The full list, with reasons and fixes, is in [known_gaps.md](known_gaps.md).

- **Only the explicit track.** Implicit lists are not supported: every list is validated as explicit, so an implicit list fails with the Table 1 rules. The base model (both kinds of list) is not used.
- **Unrecognized critical extensions are not rejected** (clause 6.3.17).
- **There is no signature validator.** Whether a signature is valid (the envelope, the JAdES / XAdES header, the signing certificate, the cryptographic signature) is not checked. The schemas check only where a signature may or must sit: no `Signature` component in a JSON list (6.8.0), `ds:Signature` optional in XML, required in an Annex H list in XML (H.4).
- **Network on first XML run:** the XSD imports `xml.xsd` and the W3C XML-DSig schema from w3.org.
- Rules-layer requirements no program can check (listed in each profile) are not checked.
